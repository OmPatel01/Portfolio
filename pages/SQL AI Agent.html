Project Overview

Most people who need data insights don't know SQL. They either wait for an analyst or they go without. This project solves that. NL → SQL Assistant is a production-grade, LLM-powered backend system that converts plain English questions into safe, optimised PostgreSQL queries and returns structured results — all without the user writing a single line of SQL.

Built in Python with FastAPI and Google Gemini 2.5 Flash, the system goes far beyond a simple "prompt → query" wrapper. It implements a multi-layer validation pipeline, schema-aware prompting, session management, cost-optimised LLM usage, and real-time confidence warnings — patterns you'd expect in a mature, production AI system.

Problem Statement

The core problem: LLMs are powerful but unreliable. A naive NL-to-SQL system just sends a user's question to an LLM and trusts the output. In practice this leads to hallucinated table names, SQL injection risks, runaway queries scanning millions of rows, and no mechanism to catch when the model produces garbage. How do you build an LLM-powered data query system that is simultaneously safe, accurate, cost-efficient, and production-ready?

This project answers that question by rethinking every stage of the pipeline — from input validation to query execution to error transparency — treating the LLM as one component within a system of guardrails rather than the system itself.

System Architecture

Every query passes through a strict, ordered pipeline. No stage is skipped, and each service has a single responsibility:

User Question → Ambiguity Check → Schema Relevance → LLM Classifier → SQL Generation → Confidence Eval → SQL Validation → Query Execution → Structured Response
Layer Module Responsibility
GeminiProvider llm/gemini_provider.py Async Gemini calls — exponential retry, fallback model, truncation detection, SQL fence stripping
ClassifierService services/classifier.py Fast-reject rules → fuzzy schema keyword match → LLM intent classification (3-layer defence)
NLToSQLService services/nl_to_sql.py Schema-injected prompt building, SQL generation, on-demand plain-English explanation
ConfidenceEvaluator services/confidence.py 6 rule-based checks post-generation: missing filters, SELECT *, ambiguous columns, strict ILIKE, etc.
SQLValidator services/validator.py Allowlist-based safety gate: blocked keywords, SELECT-only enforcement, comment injection prevention
QueryExecutor services/query_executor.py READ ONLY transaction, CTE-aware LIMIT injection, row capping, result serialisation
SchemaService services/schema_service.py Schema extraction, 1-hour TTL cache, MD5 fingerprint change detection, manual refresh

Key Features

🛡️
3-Layer Input Validation
Fast rule-based rejection → fuzzy keyword schema relevance → LLM intent classifier. Only valid, answerable queries ever reach SQL generation, saving tokens and latency on every bad request.
🧠
Schema-Aware Prompting
Live database schema (tables, columns, PKs, FKs) is injected into every Gemini prompt from a fingerprinted, TTL-cached store — preventing hallucinated columns entirely.
🔁
LLM Resilience
Exponential backoff on 503s, automatic fallback to a lighter Gemini model, and truncation detection with doubled token-budget retry — the pipeline never crashes silently on an LLM error.
⚡
CTE-Aware LIMIT Injection
Row caps are enforced in the executor layer, not the LLM. A custom paren-depth parser injects LIMIT on the outer SELECT of CTEs — not inside the CTE body, which would break the query.
💬
Conversational Context
Session history (last N turns) is injected into the SQL generation prompt, enabling natural follow-ups like "now filter that by genre = Fiction" without restating the full question.
💡
On-Demand Explanation
A dedicated /explain endpoint generates plain-English summaries only when the user requests it. Zero unnecessary LLM calls during normal query execution — cost is a first-class concern.
🔍
Fuzzy Typo Tolerance
Schema relevance uses difflib.SequenceMatcher with a 0.75 similarity threshold — "produts" still maps to "products" and isn't rejected as out-of-scope.
🗄️
Schema Caching & Fingerprinting
Schema is extracted once, cached with a 1-hour TTL, and MD5-fingerprinted. Cache refreshes only happen when the schema actually changes — not on every request.

Safety & SQL Guardrails

The SQL validator enforces a strict allowlist — no exceptions, no overrides. If a query doesn't pass, it never reaches the database:

  • Only SELECT and WITH ... SELECT (CTEs) are permitted — query must match these patterns exactly
  • Blocked keywords: INSERT, UPDATE, DELETE, DROP, ALTER, TRUNCATE, EXECUTE, GRANT, REVOKE, and more
  • No stacked statements — any semicolon appearing mid-query is an immediate rejection
  • SQL comment injection via -- and /* */ is explicitly blocked
  • Every query executes inside a READ ONLY transaction — even if a statement somehow slipped through validation, the database would refuse it at the connection level

Confidence Warning System

After SQL generation, a rule-based ConfidenceEvaluator analyses the query and emits structured, machine-readable warnings that are surfaced in the API response and shown to the user in the UI:

MISSING_FILTER SELECT_STAR AMBIGUOUS_COLUMN LARGE_RESULT LOW_CONFIDENCE STRICT_MATCH AMBIGUOUS_QUERY OUT_OF_SCOPE

For example, STRICT_MATCH uses a regex scan to catch when the LLM generates ILIKE 'Fiction' without wildcards — an exact match that would silently miss rows. The prompt enforces ILIKE '%value%' as the default, and the confidence layer catches regressions. These warnings help users understand why a result looks unexpected without exposing internal errors.

Demo Mode vs Custom Mode

The system supports two operating modes with no code changes required:

  • Demo mode — connects to a pre-seeded library management PostgreSQL database with three related tables: books, members, and borrowings. No credentials required — anyone can try it immediately.
  • Custom mode — users provide their own PostgreSQL connection string and Gemini API key via POST /session/init. Credentials are stored in-memory only, scoped to the session, and never persisted to disk. The system auto-extracts that database's schema and adapts every prompt accordingly — making the system database-agnostic.

Key Engineering Decisions & Learnings

01
LLM ≠ Reliable Infrastructure
503 errors, model deprecations, and mid-output truncation are normal. Every Gemini call is wrapped with retries, a fallback model, and truncation detection — treating the LLM as an unreliable dependency, not a magic box.
02
Backend Owns System Constraints
LIMIT clauses, safety checks, and row caps are enforced by backend code — never delegated to the LLM. Letting the model control system-level constraints is a reliability anti-pattern that breaks under real usage.
03
Cost is a First-Class Concern
Explanation generation was isolated to an on-demand endpoint. Schema relevance uses fast keyword matching before an LLM classification call. Every layer asks: does this actually need the LLM?
04
CTEs Need Special Handling
Naively appending LIMIT to a CTE truncates the inner query, not the outer one. A custom paren-depth parser identifies the outer SELECT and injects LIMIT there — a PostgreSQL-specific edge case requiring real engineering.
05
Real Users Are Messy
Typos, vague queries, partial table names — the fuzzy matching layer using difflib handles all of these, reducing false rejections and making the system genuinely usable rather than brittle.
06
Modular Design Pays Off
Every service has one job. Adding the STRICT_MATCH check, the on-demand explain endpoint, or the auto-LIMIT prompt rule each required touching exactly one file — not refactoring the whole codebase.

What Makes This Production-Grade

"I started with a simple NL-to-SQL system, but iteratively evolved it into a production-style architecture by introducing multi-layer validation, schema-aware prompting, execution guardrails, and cost-optimized LLM usage. The key learning was that LLMs must be treated as unreliable components and wrapped with strong backend controls — not trusted to handle system constraints themselves."
